# 文化祭レジ（ベビーカステラ）

Google Apps Script で動くレジアプリ。**味ごとにボタンが出て**、押すだけで会計でき、
売上はスプレッドシートに自動で溜まる。**電波が切れてもレジは動き続ける。**

```
apps/festival-pos/
  src/
    appsscript.json   マニフェスト（タイムゾーン Asia/Tokyo、ウェブアプリ設定）
    Code.gs           API・カタログ配信・売上記録・冪等化・レジ締め
    Setup.gs          シートの初期化とメンテナンス、価格の妥当性チェック
    index.html        画面構成
    style.html        スタイル
    script.html       端末側のロジック（カタログ・カート・ローカル保存・同期）
  test/
    run.sh            Node でサーバー側ロジックを検証する（60ケース）
```

---

## 1. 設計

### 同期の方向を分ける

競合が起きるのは、同じデータが双方向に流れるからである。方向を分ければ原理的に衝突しない。

```
  スプレッドシート                    レジ端末
  ┌──────────┐                  ┌──────────┐
  │  商品     │ ── カタログ ─────▶ │ 商品ボタン │   一方向
  │          │   （味と価格）     │          │
  │  売上     │ ◀── 会計 ────────  │ ローカル   │   一方向・追記のみ
  └──────────┘                  └──────────┘
```

### 価格を変えても過去の売上が動かない

売上の各行には、**会計したときの商品名と単価を「値」で焼き込む**（数式で参照しない）。

| | |
| --- | --- |
| `商品名` `区分` `単価` | 会計時点のスナップショット |
| `カタログVer` | そのときのカタログバージョン |
| `金額` | 上の単価から組み直した金額 |

これをやらないと、途中で値上げした瞬間に午前中の売上まで書き換わり、レジ締めが永久に合わなくなる。

### 変更の伝え方はタイムスタンプではなくバージョン番号

「商品」シートを編集すると `onEdit` が発火し、`CATALOG_VERSION` が 1 つ増える。
端末は 15 秒ごとの同期でこれを受け取り、値が変わっていれば商品と価格を差し替えて
ボタンとカートを作り直す。

タイムスタンプで比較しないのは、**端末の時計がずれていても壊れないようにする**ため。
時刻は「いつ売れたか」を記録するためだけに使う。

### オフラインでも売れる

会計は端末のローカル保存（`localStorage`）に即確定し、画面はすぐ次の客へ進む。
送信はバックグラウンドで行い、失敗しても未送信のまま端末に残って再送される。

再送で二重計上しないよう、**取引ごとに UUID を振り、サーバー側で重複を弾く**（冪等）。
送信がタイムアウトしたが実際にはサーバーに届いていた、という場合でも行は増えない。

> **重要な制約**
> Apps Script のウェブアプリには Service Worker を入れられないため、
> **一度タブを閉じると、電波がないあいだは開き直せない。**
> 会場に着いたら電波のあるうちにアプリを開き、そのまま閉じないこと。
> （閉じてしまっても未送信の会計は端末に残っているので、電波が戻れば送信される。）

### 打ち間違いは「取消行」で訂正する

売上シートの行は編集・削除しない。アプリの「取消」を使うと、**数量と金額をマイナスにした
取消行**が明細ぶん追加される。`SUM` すればそのまま純売上になる。

## 2. 料金ルール

**味ごとに 3個セット・7個セット・バラ単価を持つ。セット以外は常にバラ単価。**

| 買う個数 | 金額 |
| --- | --- |
| 3個ちょうど（その味の「3個」ボタン） | その味の 3個セット価格 |
| 7個ちょうど（その味の「7個」ボタン） | その味の 7個セット価格 |
| それ以外 | 個数 × その味のバラ単価 |

味もセットも組み合わせられる。
「プレーン7個 ＋ チョコ3個×2 ＋ 抹茶バラ4個」なら
`プレーン7個セット + チョコ3個セット×2 + 4 × 抹茶バラ単価`。

> **注意**: このルールだと、バラ単価によっては **6個がセット7個より高くなる**ことがある。
> 例）バラ ¥120・7個セット ¥600 → バラ6個 ¥720 > 7個セット ¥600
> メニュー「レジ管理 → 設定をチェック」が**味ごとに**これを検出して警告する。
> 価格を見直すか、6個のお客さんには7個セットを案内すること。

## 3. セットアップ

1. 新しい Google スプレッドシートを作る
2. **拡張機能 → Apps Script** を開き、`src/` の中身を同名で貼り付ける
   - `Code.gs` `Setup.gs` … スクリプトファイル
   - `index.html` `style.html` `script.html` … HTML ファイル（「ファイル → HTML」で作る）
   - `appsscript.json` … ⚙ プロジェクトの設定 →「マニフェスト ファイルをエディタで表示する」にチェック
3. スプレッドシートを開き直すとメニュー「**レジ管理**」が出る
4. 「**レジ管理 → シートを初期化 / 修復**」を実行する（パスコードが自動生成される）
5. 「**商品**」シートに味ごとの行を作る

   | 商品名 | 3個セット | 7個セット | バラ1個 | 販売状態 | 備考 |
   | --- | --- | --- | --- | --- | --- |
   | プレーン | ¥300 | ¥600 | ¥120 | 販売中 | |
   | チョコ | ¥350 | ¥700 | ¥140 | 販売中 | |
   | 抹茶 | ¥400 | ¥800 | ¥160 | 停止中 | 焼き上がり待ち |

   - **商品名がキー**。同じ名前を 2 行書くと、下の行は無視される（設定チェックが警告する）
   - **販売状態を「停止中」にすると、その味のボタンがレジから消える**（売切れ・焼き上がり待ちに使う）
   - 行を足すだけで味を増やせる。コードの変更は不要

6. 「**レジ管理 → 設定をチェック**」で価格の妥当性を確認する
7. **デプロイ → 新しいデプロイ → 種類「ウェブアプリ」**
   - 次のユーザーとして実行: **自分**
   - アクセスできるユーザー: **全員**
8. 発行された URL をレジ端末で開く

> URL を知っていれば誰でも開けるので、パスコードは必ず設定すること。
> **URL を SNS などに貼らないこと。**

## 4. 当日の使い方

### 開店前

1. 電波のあるところでアプリを開く
2. **担当者名**・**パスコード**・**釣銭準備金**を入力して「レジを開く」
3. そのままタブを閉じない（端末の自動ロックはアプリ側で抑止を試みるが、端末設定でも切っておくと確実）

### 会計

1. 味ごとのカードにある「3個」「7個」「バラ」を押す
   - 押した数はボタン右上のバッジに出る
   - カートの ＋ − で数量を調整できる
2. お預かりを入力（「ちょうど」「1,000」などのボタンでも可）
3. **おつりが大きく表示される**
4. 「会計する」

右上のバッジで状態がわかる。

| 表示 | 意味 |
| --- | --- |
| 同期済 | すべてスプレッドシートに届いている |
| 未送信 N | N 件がまだ送れていない（自動で再送される） |
| オフライン N | サーバーに届かない。会計は続けられる |

### 途中で味や価格を変えたとき

「商品」シートを直すだけ。最大 15 秒で全端末のボタンと価格が入れ替わり、
画面上部に「商品・価格が変更されました」と出る。
**会計途中のカートは新しい価格で計算し直される**（まだお金を受け取っていないため）。
すでに済んだ会計の金額は変わらない。

売っている途中の味を「停止中」にした場合、その味がカートに残っている端末では
「販売停止」と表示されたまま会計できる（最後に読み込んだ単価を使う）。

### 打ち間違い

メニュー（☰）→ **会計履歴・取消** → 該当の会計の「この会計を取り消す」

### 閉店・交代

- **レジ締め**: メニュー → レジ締め → 実際に数えた現金を入力 → 差額が記録される
  - 未送信の会計が残っていると記録できない。電波のある場所で「いますぐ同期」を先に実行する
- **担当者交代**: メニュー → 担当者を交代

## 5. シート構成

| シート | 内容 |
| --- | --- |
| ダッシュボード | 売上金額・販売個数・会計件数・**商品別**・区分別・担当者別・時間帯別（すべて数式） |
| 商品 | 味ごとの価格と販売状態。**ここを直すとレジのボタンが変わる** |
| 設定 | 店名とパスコード。黄色セルだけ編集する |
| 売上 | **1 行 = 1 明細。**編集・削除しない |
| レジ締め | シフトごとの釣銭準備金・理論現金・実査現金・差額 |

### 売上シートの列

1 回の会計が複数行になる。同じ `取引ID` の行がひとつの会計で、
取引単位の値（`取引合計` `お預かり` `お釣り` `検証` `備考`）は**先頭明細行にだけ**入る。

| 列 | 内容 | | 列 | 内容 |
| --- | --- | --- | --- | --- |
| A | 受信日時（サーバー時刻） | | K | 数量（セット数 / バラ個数） |
| B | 取引ID（冪等キー） | | L | 個数（3個セットなら 3×数量） |
| C | 明細番号（1 から） | | M | 単価スナップショット |
| D | 端末ID | | N | 金額 |
| E | 担当者 | | O | カタログVer |
| F | 会計日時（端末時刻） | | P | 取引合計 ※先頭行のみ |
| G | 種別（売上 / 取消） | | Q | お預かり ※先頭行のみ |
| H | 取消元取引ID | | R | お釣り ※先頭行のみ |
| I | 商品名スナップショット | | S | 検証 ※先頭行のみ |
| J | 区分（3個セット / 7個セット / バラ） | | T | 備考 ※先頭行のみ |

売上合計は `SUM(N:N)`、販売個数は `SUM(L:L)`、会計件数は `明細番号 = 1` の行を数える。

**検証**列は、端末が計算した金額とサーバーが単価から組み直した金額が一致するかを示す。
`OK` 以外が出たらバグなので調べること。

A（サーバー時刻）と F（端末時刻）を分けているのは、端末の時計がずれていても
「実際に届いた順番」を追えるようにするため。

## 6. テスト

実機にデプロイせず、サーバー側のロジックを Node で検証できる。

```sh
sh apps/festival-pos/test/run.sh
```

- `pricing.test.js`（33ケース）… 味ごとの単価、味をまたいだ会計、明細行の組み立て、
  取消がマイナスになること、値上げ後に届いた古い会計が古い単価のまま記録されること、
  不正な明細を落とすこと
- `idempotency.test.js`（27ケース）… カタログ配信（重複行の先勝ち、停止中の扱い）、
  同じ取引 ID を何度送っても二重計上しないこと、複数明細でも取引単位で冪等なこと、
  パスコード検証、空バッチでロックを取らないこと

## 7. 積み残し・検討事項

- **現金以外の決済**（PayPay 等）は未対応。記録するなら売上シートに「決済手段」列を足し、
  レジ締めの理論現金から除外する必要がある
- **在庫数の管理**は未実装。「販売状態」で売切れを止めることはできるが、残数は数えていない
- **複数端末で 1 つの金庫を共有する場合**、レジ締めは端末ごとの理論値になるため合わない。
  端末ごとに金庫を分けるか、締めは合算で手計算すること
- 端末のローカル保存は `localStorage`。**端末のブラウザのデータを消すと未送信分が失われる**ので、
  こまめに同期すること
- 味が 10 種類を超えると 1 画面に収まらずスクロールが増える。
  その場合はカテゴリ分けや「よく出る味」の並べ替えを検討する
