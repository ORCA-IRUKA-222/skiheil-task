# 文化祭レジ（ベビーカステラ）

Google Apps Script で動くレジアプリ。ボタンを押すだけで会計でき、売上はスプレッドシートに自動で溜まる。
**電波が切れてもレジは動き続ける。**

```
apps/festival-pos/
  src/
    appsscript.json   マニフェスト（タイムゾーン Asia/Tokyo、ウェブアプリ設定）
    Code.gs           API・売上記録・冪等化・レジ締め
    Setup.gs          シートの初期化とメンテナンス、価格の妥当性チェック
    index.html        画面構成
    style.html        スタイル
    script.html       端末側のロジック（カート・ローカル保存・同期）
  test/
    run.sh            Node でサーバー側ロジックを検証する
```

---

## 1. 設計

### 同期の方向を分ける

競合が起きるのは、同じデータが双方向に流れるからである。方向を分ければ原理的に衝突しない。

```
  スプレッドシート                    レジ端末
  ┌──────────┐                  ┌──────────┐
  │  設定     │ ── 価格 ────────▶ │ 価格      │   一方向
  │          │                  │          │
  │  売上     │ ◀── 会計 ────────  │ ローカル   │   一方向・追記のみ
  └──────────┘                  └──────────┘
```

### 価格を変えても過去の売上が動かない

売上の各行には、**会計したときに適用した単価を「値」で焼き込む**（数式で参照しない）。

| | |
| --- | --- |
| `単価(3個)` `単価(7個)` `単価(バラ)` | 会計時点の単価 |
| `価格Ver` | そのときの価格バージョン |
| `合計金額` | 上の単価から組み直した金額 |

これをやらないと、途中で値上げした瞬間に午前中の売上まで書き換わり、レジ締めが永久に合わなくなる。

### 価格変更の伝え方はタイムスタンプではなくバージョン番号

「設定」シートの価格セルを編集すると `onEdit` が発火し、`PRICE_VERSION` が 1 つ増える。
端末は 15 秒ごとの同期でこれを受け取り、値が変わっていれば価格を差し替えてカートを計算し直す。

タイムスタンプで比較しないのは、**端末の時計がずれていても壊れないようにする**ため。
時刻は「いつ売れたか」を記録するためだけに使う。

### オフラインでも売れる

会計は端末のローカル保存（`localStorage`）に即確定し、画面はすぐ次の客へ進む。
送信はバックグラウンドで行い、失敗しても未送信のまま端末に残って再送される。

再送で二重計上しないよう、**取引ごとに UUID を振り、サーバー側で重複を弾く**（冪等）。
送信がタイムアウトしたが実際にはサーバーに届いていた、という場合でも行は増えない。

> **重要な制約**
> Apps Script のウェブアプリには Service Worker を入れられないため、
> **一度タブを閉じると、電波がないあいだは開き直せない。**
> 会場に着いたら電波のあるうちにアプリを開き、そのまま閉じないこと。
> （閉じてしまっても未送信の会計は端末に残っているので、電波が戻れば送信される。）

### 打ち間違いは「取消行」で訂正する

売上シートの行は編集・削除しない。アプリの「取消」を使うと、**数量と金額をマイナスにした取消行**が
追加される。`SUM` すればそのまま純売上になる。

## 2. 料金ルール

**セット以外は常にバラ単価。**

| 買う個数 | 金額 |
| --- | --- |
| 3個ちょうど（3個ボタン） | 3個セット価格 |
| 7個ちょうど（7個ボタン） | 7個セット価格 |
| それ以外 | 個数 × バラ単価 |

セットとバラは組み合わせられる。「7個ボタン＋バラ3個」なら `7個セット価格 + 3 × バラ単価`。

> **注意**: このルールだと、バラ単価によっては **6個がセット7個より高くなる**ことがある。
> 例）バラ ¥120・7個セット ¥600 → バラ6個 ¥720 > 7個セット ¥600
> メニュー「レジ管理 → 設定をチェック」がこれを検出して警告する。
> 価格を見直すか、6個のお客さんには7個セットを案内すること。

## 3. セットアップ

1. 新しい Google スプレッドシートを作る
2. **拡張機能 → Apps Script** を開き、`src/` の中身を同名で貼り付ける
   - `Code.gs` `Setup.gs` … スクリプトファイル
   - `index.html` `style.html` `script.html` … HTML ファイル（「ファイル → HTML」で作る）
   - `appsscript.json` … ⚙ プロジェクトの設定 →「マニフェスト ファイルをエディタで表示する」にチェック
3. スプレッドシートを開き直すとメニュー「**レジ管理**」が出る
4. 「**レジ管理 → シートを初期化 / 修復**」を実行する
5. 「**設定**」シートの黄色セルを埋める

   | キー | 内容 |
   | --- | --- |
   | `PRICE_SET3` | 3個セットの価格 |
   | `PRICE_SET7` | 7個セットの価格 |
   | `PRICE_SINGLE` | バラ1個の価格 |
   | `SHOP_NAME` | アプリ上部に出る店名 |
   | `PASSCODE` | アプリを開くときのパスコード（初期化時に 4 桁がランダム生成される。変更可） |

6. 「**レジ管理 → 設定をチェック**」で価格の妥当性を確認する
7. **デプロイ → 新しいデプロイ → 種類「ウェブアプリ」**
   - 次のユーザーとして実行: **自分**
   - アクセスできるユーザー: **全員**
8. 発行された URL をレジ端末で開く

> URL を知っていれば誰でも開けるので、`PASSCODE` は必ず設定すること。
> **URL を SNS などに貼らないこと。**

## 4. 当日の使い方

### 開店前

1. 電波のあるところでアプリを開く
2. **担当者名**・**パスコード**・**釣銭準備金**を入力して「レジを開く」
3. そのままタブを閉じない（端末の自動ロックはアプリ側で抑止を試みるが、端末設定でも切っておくと確実）

### 会計

1. 「3個」「7個」「バラ +1」を押す（カートの ＋ − で数量調整、「バラ +5 / +10」もある）
2. お預かりを入力（「ちょうど」「1,000」などのボタンでも可）
3. **おつりが大きく表示される**
4. 「会計する」

右上のバッジで状態がわかる。

| 表示 | 意味 |
| --- | --- |
| 同期済 | すべてスプレッドシートに届いている |
| 未送信 N | N 件がまだ送れていない（自動で再送される） |
| オフライン N | サーバーに届かない。会計は続けられる |

### 打ち間違い

メニュー（☰）→ **会計履歴・取消** → 該当の会計の「この会計を取り消す」

### 閉店・交代

- **レジ締め**: メニュー → レジ締め → 実際に数えた現金を入力 → 差額が記録される
  - 未送信の会計が残っていると記録できない。電波のある場所で「いますぐ同期」を先に実行する
- **担当者交代**: メニュー → 担当者を交代

## 5. シート構成

| シート | 内容 |
| --- | --- |
| ダッシュボード | 売上金額・販売個数・会計件数・商品別・担当者別・時間帯別（すべて数式） |
| 設定 | 価格とパスコード。黄色セルだけ編集する |
| 売上 | 1 行 1 会計。**編集・削除しない** |
| レジ締め | シフトごとの釣銭準備金・理論現金・実査現金・差額 |

### 売上シートの列

| 列 | 内容 | | 列 | 内容 |
| --- | --- | --- | --- | --- |
| A | 受信日時（サーバー時刻） | | K | 合計個数 |
| B | 取引ID（冪等キー） | | L〜N | 単価スナップショット |
| C | 端末ID | | O | 価格Ver |
| D | 担当者 | | P | 合計金額 |
| E | 会計日時（端末時刻） | | Q | お預かり |
| F | 種別（売上 / 取消） | | R | お釣り |
| G | 取消元取引ID | | S | 検証 |
| H〜J | 3個 / 7個 / バラ の数量 | | T | 備考 |

**検証**列は、端末が計算した金額とサーバーが単価から組み直した金額が一致するかを示す。
`OK` 以外が出たらバグなので調べること（ダッシュボードの「検証NG」で件数を監視できる）。

A（サーバー時刻）と E（端末時刻）を分けているのは、端末の時計がずれていても
「実際に届いた順番」を追えるようにするため。

## 6. テスト

実機にデプロイせず、サーバー側のロジックを Node で検証できる。

```sh
sh apps/festival-pos/test/run.sh
```

- `pricing.test.js` … 料金計算、取消がマイナスになること、
  価格変更後に届いた古い会計が古い単価のまま記録されること
- `idempotency.test.js` … 同じ取引 ID を何度送っても二重計上しないこと、
  パスコード検証、空バッチでロックを取らないこと

## 7. 積み残し・検討事項

- **現金以外の決済**（PayPay 等）は未対応。記録するなら売上シートに「決済手段」列を足し、
  レジ締めの理論現金から除外する必要がある
- **在庫・売切れ管理**は未実装。焼き上がり待ちのあいだ会計を止める機能が要るなら追加する
- **複数端末で 1 つの金庫を共有する場合**、レジ締めは端末ごとの理論値になるため合わない。
  端末ごとに金庫を分けるか、締めは合算で手計算すること
- 端末のローカル保存は `localStorage`。**端末のブラウザのデータを消すと未送信分が失われる**ので、
  こまめに同期すること
